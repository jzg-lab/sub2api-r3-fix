## 目标与已对齐规则

把“账号是否允许客户调度”与“某个分组能否使用该账号”分开。
用户已确认：混合账号的总调度按最宽松分组处理；严格分组仍执行自己的质量要求。
普通分组可以使用质量未通过但其他条件正常的账号，严格分组不可以。
“可以开启”不等于系统替用户自动开启；人工暂停和其他正常限制不受此规则影响。

| 账号所属业务分组 | 质量失败后的总调度 | 严格分组准入 | 普通分组准入 |
| --- | --- | --- | --- |
| 全部严格 | 沿用质量停调与独立救治 | 不放行 | 不适用 |
| 严格与普通混合 | 不因质量失败整体停调，允许管理员开启 | 不放行 | 其他条件正常时可用 |
| 全部普通 | 不因质量失败强制停调或自动入区 | 不适用 | 其他条件正常时可用 |

严格分组无合格账号时返回无可用账号，不降格使用普通分组中的不合格账号。
无分组按普通处理；停用、已删除和内部救治分组不作为“宽松业务分组”的依据。
在区账号按原业务分组快照判断，而不是把 rescue-lab 误认为普通分组。
具体可用分组集合由宿主实际分组绑定及正常可用条件确定，不按分组名称猜测。
仅绑定停用/删除分组不产生新的客户路由权限；“按普通处理”不创建任何新分组绑定。

## 现状与修改边界

现有账号只有一个全局 `schedulable`，并非每组各有开关。救治入区会原子改绑独立组、
停调并保存原组；普通开启操作遇到救治标记会被仓库层拒绝。后台资格失败也会停调，
因此只改插件表单、只放开手动开关、只限制自动入区都不能实现目标。

第一版范围为现有 OpenAI OAuth 质量检测对象；其他平台、API Key 及影子账号的基础
规则不改变。影子/母账号的共享健康路径必须检查，不能让新策略绕过已有父账号保护。
若严格分组还包含未支持质量检测的账号类型，界面应明确范围，不能宣称整组已获保证。

Cookie 捕获、白名单合并、按账号保存、代理、凭据与签名安装规则保持原样。
本次选择的是质量强制保护分组，不是 Cookie 本身的注入分组；不承诺上游会话按组隔离。

## 设置与界面

第一版只增加“分组质量保护”总开关与“保护分组”多选，不增加第三套观察状态机。
选中为严格，未选中为普通。关闭强制保护不等于关闭 Cookie 或质量探针。
关闭保护或调整选组不自动解除人工暂停，也不直接开启历史停调账号。

策略由宿主保存和执行，复用现有 settings 的类型化 JSON 与管理 API 校验模式，
不让插件持有数据库/调度写权限，也不把宿主策略混存到第三方插件配置。
管理入口放在插件管理页面的宿主区域；使用原有分组列表与保存/审计机制，
不扩展 iframe 通用权限或绕过保存认证。对无效、已删除或不适用的组 ID 拒绝保存。

保存前预览严格账号、混合账号及已有救治账号数量；显示总调度限制与分组质量限制
各自的具体原因。账号处于质量观察/恢复中但可服务普通分组时，不再显示为全局不可用。

配置缺失与显式关闭必须区分。新程序安装后、用户尚未明确启用新策略前维持旧行为；
不能将缺失配置解释为空选组而突然全池放行。显式开启且选组为空应明确确认其无保护含义。

## 开发顺序与交付物

按 P1 至 P6 顺序实现并分段验证，形成一个完整发布版本。P2 的分组过滤完成前，
不能在生产单独启用 P3 的混合账号放行，否则严格组会接到未经验证的账号。

### P1：策略配置与影响预览

- [ ] 在宿主现有 settings 中增加独立类型化 JSON 设置，建议键名 `openai_quality_policy`。
  业务字段仅含 `enabled` 和 `protected_group_ids`；配置缺失表示沿用旧行为。
  已保存且 `enabled=false` 表示不执行质量强制保护，不能与“未配置”混为一谈。
- [ ] 复用 OpenAI 管理路由及设置服务模式，提供读取、保存和影响预览接口。
  建议放在 `/api/v1/admin/openai-operations/quality-policy`，预览用其 `/preview` 子路径。
  设置读取可回传服务端版本，保存校验旧版本，避免两个后台页面互相覆盖。
- [ ] 校验分组 ID、去重、权限、保存失败回显；预览输出严格/混合/普通及存量隔离账号。
  使用已有组 ID，与名字、颜色、排序无关；保存不修改账号调度位。
- [ ] 统一业务组分类与质量限制判定，供选号、手动开关、检测提交、救治清扫共用。
  配置读失败不当作显式关闭；正常基础控制未知时沿用 fail-closed。

交付：设置读写/预览可验证，配置缺失、显式关闭、空选组各自行为明确；
复用现有 settings 持久化，不新增每账号每分组探针表或通用策略引擎。

### P2：分组选号与请求终检

- [ ] 在共享选号和最终出站检查处接入质量准入；质量证据按账号保存，按请求分组使用。
  严格组只放行符合当前检测标准的账号，普通组仍检查原有账号权限、人工开关及基础限制。
- [ ] 覆盖普通/高级调度、会话粘性、previous_response、重试、并发等待后的再检查、
  HTTP/WS、备用组和适用的组合路由。严格要求沿整个请求路径传递，不能经备用组降格。
- [ ] 复用既有缓存/快照及失效通知，避免逐候选访问数据库或逐请求询问插件进程。
  配置、分组、证据变化后刷新相关结果；缓存不能把普通组准入结论复用于严格组。
- [ ] 已开始的上游请求正常完成；等待与尚未出站的请求按最新版本终检。
  无合格账号返回明确的不可用原因，不能清空排除条件重试。

交付：同一个质量失败账号，在正常开启且无其他阻断时，普通组可选、严格组不可选；
所有替代选号路径得到相同结果。

### P3：检测副作用与救治编排

- [ ] 梳理质量、凭据、限流、网络/代理、人工控制的现有结果分类。
  纯质量失败对混合/普通账号只更新证据与质量状态，不整体停调、自动搬组或改变共享代理。
  凭据拒绝、限流、到期、代理故障和人工暂停继续执行各自正常保护。
- [ ] 手动开启、批量编辑、自动入区钩子及周期清扫使用同一策略。
  混合账号已允许服务普通组后，后续检测和清扫不能再次把它整体关闭。
- [ ] 为混合账号接通现有资格/恢复检测流程，不能因没有救治区标记或处于 pending_replace
  就永远不复测。检测结果可恢复严格组准入，但不能顺带开启人工关闭的账号。
- [ ] 将“恢复质量证据”与“恢复原组并开启整体调度”分开。
  当前 `qualificationReady` 对无救治标记账号直接返回 true，不能把删除标记当作
  混合账号质量恢复。复用现有检测记录及可持久化的恢复轮次/身份依据，保持迟到结果隔离。
- [ ] 严格独占账号保留原子入区/毕业及原组快照。手动与自动入口都复核范围；
  用户显式暂停/终止不会被策略切换清除。检测提交、入区和毕业同时校验账号/分组/策略版本。

交付：普通组业务可以继续，严格组资格仍可独立恢复；原有认证保护与人工控制不回退。
初始资格沿用现有判定，质量恢复沿用当前轮次宿主和插件联合证据。
证据有效期与真实探测周期一起验收，不能把救治区 15 分钟窗口机械套给所有常规账号。

### P4：存量账号过渡

## 历史账号过渡

先只读导出已有停调与救治账号的原组、优先级、人工暂停/终止和停调原因，形成预览。
由用户确认需要释放的账号，再通过原生原子生命周期操作恢复原组并保留优先级、
其他配置和审计；不手改 account_groups，不删除原标记伪装恢复，不全池开启。

原组损坏/删除、原因不明、人工暂停/终止、凭据失效等账号留待人工处理。
因策略变更退出质量隔离不算“质量已恢复”，不增加复活计数、不生成已复活徽标。
放行普通组后的质量失败证据保留，严格组仍不能选中。
后续分组变更必须重新计算策略；添加/删除普通组不能偷改人工开关或让旧回调重启账号。
即使允许有意添加普通组放宽规则，也需既有管理员权限、影响预览及正常审计。

## 验收与上线

必须覆盖的用例：

- 同一混合账号：普通组可选，严格组拒绝，手动总开关可以保存。
- 严格独占账号：失败停调；恢复需合格证据，原组/优先级原子还原。
- 普通独占账号：质量失败不关调度、不自动救治；原有正常限制仍生效。
- 粘性、备用组、等待后终检、高级/旧调度、HTTP/WS 均不能绕过严格要求。
- 停用/删除/内部组不会误触发宽松规则；分组与策略变化、缓存过期、迟到结果不误放行。
- 配置缺失、显式关闭、开启空列表、证据缺失/失效与插件离线得到不同且明确的结果。
- 历史账号迁移不解除人工暂停/终止、不清空证据、不误记恢复成功。

上线顺序：本地回归与隔离集成验收；备份当前策略及相关账号快照；部署宿主但保留旧行为；
预览并确认初始保护组；灰度切换一个保护组和少量账号；确认两类流量结果后扩大范围。
切换前确认所有提供流量和运行后台检测的实例均已支持新策略，旧实例不能继续按旧逻辑停调。
真实请求测试的账号、次数/token 预算在灰度前单独确认，不把此前全账号测试授权当无限预算。
本次不默认修改插件主动探针开关/频率，不承诺主动请求消耗已经下降。

需部署新版宿主与对应前端；第一版不要求修改 Cookie 插件二进制或协议。
若实施中发现现有插件主动探针范围必须配套控制，先明确扩展范围与成本，不悄悄把它加入。

回退不能仅换回旧程序：旧程序不理解新版按组质量限制。必须先阻断严格组的不安全入口
并失效相应缓存，或将受影响账号转为旧版可理解的安全隔离，再回退；这可能暂时影响
普通组可用性，应提前说明。只还原本轮相关配置/账号，不用整库旧备份覆盖新业务数据。

规则方向已确认，无需重复确认“混合账号按最宽松、严格组仍独立过滤”。
上述 P1 至 P6 方案已撤回，不再继续执行。
新的最小方案待明确要取消的限制及质量保证边界后另行制定。
