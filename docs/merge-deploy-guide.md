# 合并与部署更新指南

目标：提前准备好新镜像及验收、回退材料，在最短必要维护窗口内完成一次应用切换。
用户要求尽量不动现有环境，但必要的备份、兼容检查和迁移不能省略。
本指南长期维护；每次出现新的返工原因，都把预防措施补到这里，不另建日期版指南。

## 适用范围与记录入口

- 合并范围、个人要求和授权以 [产品规则](upstream-integration-policy.md) 及用户最新答复为准。
  已授权的事项直接执行，不重复询问；新冲突或超出范围的操作先沟通。
- 实现和回归入口见 [当前实现](local-customizations.md)；来源及合并历史写入
  [版本记录](upstream-sync-state.md)，当前线上身份和回退资源写入 [部署状态](deployment-state.md)。
- 本指南用于已有服务更新。不要对现网重新执行初始化安装脚本或覆盖 `.env`、Compose、密钥。
  单服务器更新不等于正式多平台 Release；后者另遵守 [发布要求](../RELEASE-POLICY.md)。

## 后续如何发起部署

- 正常更新时，把已推送到 GitHub 的**完整提交 SHA**发来并明确说“部署”。无需自己登录服务器操作；按该 SHA 固定构建，不跟随可能变化的 `main`。
- 服务器源码同步命令见第 2 节；它只更新源码，不会部署或重启。代码已合并推送时，按第 2–5 节完成部署核对、准备、切换和验收；需要合并时才执行第 1 节。
- 迁移或数据影响超出已确认范围时，先说明具体影响再决定是否继续；否则按清单完成切换前检查。
- 用户明确要求切换前停住时，只完成构建、签名、备份、脚本和只读检查；不得启动维护、停用插件或
  创建会执行实际切换的任务。聊天自身经过待更新网关时，将切换与条件回退准备为服务器独立
  `systemd` 任务，明确日志和结果路径；等待用户继续后启动，不能依赖后续模型回复完成恢复。
  独立任务解决的是控制连接中断后的继续执行，不代表零停机，也不保证所有故障都能自动回退。

## 已确认的部署改进范围

用户于 2026-10-20 确认：优先同机、允许短暂维护，不增加服务器；第一期先实现稳定快速部署，
第二期再接页面按钮。已有请求未排空就延后，不以强杀换取固定几秒。十秒级维护是优化目标，
须经演练确定实际时间，不是三秒保证；失败回退单独计时。

第一期实施范围（最初为本地实现；用户随后于 2026-10-20 授权提交、推送并在验收通过后直接部署）：

1. 将部署流程固化为可复用的准备、切换、状态和回退工具，凭据、备份和回执留在私有目录。
   快速通道只接收无迁移、插件不变、运行环境兼容的版本；插件升级或环境变更仍走专项流程。
2. 从完整提交提前构建制品，固定源码、运行环境和摘要；准备期间旧服务继续运行，维护期间不构建。
3. 正式修复插件相对状态路径兼容，保持实际目录及签名/持久保护不变。
4. 保留 `/health`，新增真正的就绪检查，核对初始化、数据库、Redis 和已启用插件。
5. 切换前暂停已确认的直连调用方，短窗口排空失败则恢复入口并延后；通过后才停止旧应用。
   成功或兼容回退后自动恢复原本运行的服务，聊天断连不影响执行。
6. 隔离验证直连请求、相对路径、验收客户端不一致和插件错配等失败分支；本地通过不冒充生产演练。

暂不实施双实例切流、数据库/Redis 升级、插件多实例状态改造或页面一键更新。
页面更新器仍不能直接指向官方包替换定制版。第一期工具、使用条件及验证边界见下一节；
本轮已接入服务器，首次排空延后后重新准备并成功部署；工具接入、隔离验证和生产发布仍分别记录。

## 第一期工具与操作流程

本期提供 [构建工具](../deploy/build_fast_release.py)、[部署工具](../deploy/fast_deploy.py)、
[运行镜像模板](../deploy/FastRuntime.Dockerfile)、[私有配置示例](../deploy/fast-deploy.example.json)
及 [Nginx 维护入口示例](../deploy/fast-deploy-nginx.conf.example)。只支持本机 Linux Docker Compose、
单应用实例和 systemd；不做通用集群发布平台，不修改业务配置、升级插件或恢复整库。

### 首次接入条件

以下是正式使用工具前的一次性准备；实际接入结果以部署状态中的当次证据为准：

- 提交并按授权推送本期源码后，固定完整 SHA。候选必须包含 `/readyz`；未提交工作区不能作为构建输入。
- 目标机器需要 Python 3.9+、Docker/Compose v2、使用本机镜像的 Docker 构建器、Git、tar、curl、
  Nginx 与支持 `StandardOutput=append:` / `Type=exec` 的 systemd。运维工具按 root 身份执行。
  构建须核对磁盘、内存及资源限额；本工具不自动决定生产机器可以承受的构建负载。
- 在**所有实际接入的 Nginx server 块**正确位置安装维护文件判断，核对已有 rewrite、重定向与缓存配置，
  单独批准后 `nginx -t`、reload 并演练。维护由文件存在与否控制，正常更新无需反复改写/reload Nginx。
  示例不能不经审查整段覆盖现有配置；确认 Nginx worker 可访问维护标记的父目录。
- 将实际所有 HTTPS 入口填入 `public_urls`；示例只有主域名，不代表已覆盖聊天专用域名或内网入口。
  准备检查 `/__deploy_guard` 返回 204；真正切换关闭入口后要求各入口返回 503，否则不停止旧应用。
  受 IP 限制的 HTTP 直连入口使用 `guard_checks` 检查已有路径，正常保持 403、维护时 503，
  不添加绕过原 ACL 的可访问业务入口；这里只允许回环地址。旧域名不可达时先确认使用范围。
- 盘点能绕过 Nginx 的服务、timer、内网直连及自动重启来源。只在用户批准范围内填写 `pause_services`，
  不允许外部直接打到未受控的应用端口。持续直连、长 WebSocket 或 keepalive 可能使本次更新延后，
  不能将三个零计数样本解释为能够阻止所有未知调用方。
  被暂停的服务必须有可恢复的 unit 定义；一次性 `systemd-run` 临时服务停止后可能被卸载。
  隔离演练的模拟调用方也应使用持久的服务定义，不把临时服务消失误判为生产恢复逻辑故障。
- `.env` 必须有且仅有一条普通 `SUB2API_IMAGE=镜像`，Compose 应用确实使用它。凭据、配置、
  回执、镜像清单和备份放仓库外的 0700 私有目录；`admin_header_file` 为 0600 文件，内容为正常
  管理员 API Key 的 `x-api-key: ...` 请求头。工具只用于正常只读管理接口，不提供鉴权或二次验证绕过。
  运行容器的 Compose 配置 hash 必须与当前渲染结果一致；有未应用配置或 Compose 版本导致的
  hash 差异时先核查，不自动重建来消除差异。构建/备份目录没有自动清理，按保留策略人工回收。
- 生产旧版没有 `/readyz` 时，显式设 `previous_has_readyz=false`，旧版验收仍检查健康、制品、
  插件、管理员鉴权与前端；候选版一律要求就绪成功。之后部署应设为 `true`，不是自动降级为 `/health`。
  `migration_aliases` 示例只对应现有九条已核实的历史别名，须与当前迁移器对照，不能借此放行未执行迁移。

### 准备阶段：服务继续运行

以下变量均由当次核验确定；`NEW_SHA`、`OLD_SHA` 是完整提交，`OLD_IMAGE` 是已核对的运行镜像，
`NODE_IMAGE`、`GO_IMAGE` 必须带固定 `@sha256:...`。`BUILD`、`RELEASE` 是仓库外全新私有目录，
不要复用过去已尝试的发布目录。

```sh
python3 deploy/build_fast_release.py \
  --repo /opt/sub2api-source --output "$BUILD" \
  --commit "$NEW_SHA" --previous "$OLD_SHA" --runtime "$OLD_IMAGE" \
  --node-image "$NODE_IMAGE" --go-image "$GO_IMAGE"

install -d -m 700 "$RELEASE"
python3 deploy/fast_deploy.py evidence-template --release "$RELEASE" \
  --config "$PRIVATE_CONFIG" --artifact "$BUILD/artifact.json"
```

构建从 Git archive 取固定源码，不受脏工作区影响；提前构建内嵌前端和应用，运行相关后端测试，
在旧运行镜像上只替换程序及资源，保留浏览器、Node/Python、插件目录、用户与入口设置。
部署版本在源码 SemVer 后追加 `fast.<SHA>` 构建元数据，不能用 `deploy.<SHA>` 替代合法版本，
否则插件最低宿主版本检查会拒绝。Go 测试在挂载相同模块缓存的 BuildKit 阶段执行；缓存挂载不会
保留在 builder 镜像中，直接启动断网 builder 容器运行测试会因依赖缺失而失败。
完整后端测试还需要仓库 `deploy/client-identity` 资料及 `/usr/bin/true` 测试替身路径；仅在测试阶段
补齐，不能跳过失败测试或将测试依赖混入沿用的运行镜像。
迁移 SQL/迁移器、插件包/协议、Go 依赖、Dockerfile、浏览器/客户端运行资源变化会被拒绝，
进入专项流程。此静态检查不是兼容性证明，宿主业务行为仍须核验。构建不是正式五平台 Release。

`artifact.json` 记录新旧源码、镜像及运行基底 ID、二进制、前端资源摘要、迁移清单与构建输入。
`evidence-template` 只生成 **`not_run` 模板**，不会声称测试通过。对最终候选在隔离环境完成以下检查，
把实际日志保存在发布目录并记录 SHA-256，再将对应状态记为 `passed`：

| 回执检查项 | 必须记录的实际证据 |
| --- | --- |
| `runtime_uid_paths` | 最终镜像、实际 UID/工作目录、相对与绝对插件目录；不挂生产数据 |
| `plugin_rpc_existing_config` | 同签名插件包及现有配置副本的 RPC/Host HTTP/健康；保留原保护与信任 |
| `startup_readiness` | 隔离数据库/Redis 的启动和就绪；依赖或插件不可用时 503；前端资源一致 |
| `compatible_rollback` | 同插件、同结构的新旧宿主往返与失败分支，不能只验证新宿主可启动 |
| `direct_callers_inventory` | 已批准暂停的直连服务、timer/监督进程及端口暴露核对结果 |
| `nginx_guard` | 所有入口上的维护判断、正常 TLS、普通 curl 路径；首次接入的实际测试记录 |

回执绑定源码、基底、新镜像、程序、私有配置和实际插件清单。程序验证身份与日志摘要，
不自动证明日志中的结论；维护者必须检查真实执行结果，禁止手填假通过或拿旧镜像的回执替代。
真实供应商调用、压力测试及完整数据库恢复演练仍单独列明，不由这些检查冒充。

```sh
python3 deploy/fast_deploy.py prepare --release "$RELEASE" \
  --config "$PRIVATE_CONFIG" --artifact "$BUILD/artifact.json"
python3 deploy/fast_deploy.py status --release "$RELEASE"
```

`prepare` 核对现有镜像/提交、Compose 对象与有效配置、历史迁移、插件、所有公网路径，
保存私有配置快照，执行 `pg_dump -Fc`、SHA-256 和同版本 `pg_restore --list` 检查。
同时冻结切换脚本与准备文件摘要。此阶段不关闭入口、不暂停服务、不重启应用，也不创建切换任务。
用户要求“切换前停住”时，到此为止。备份默认两小时过期，过期或材料变化须重新准备。

### 批准后的切换与回退

```sh
python3 "$RELEASE/tools/fast_deploy.py" activate --release "$RELEASE"
python3 "$RELEASE/tools/fast_deploy.py" status --release "$RELEASE"
```

`activate` 只启动服务器独立 systemd 任务；SSH/聊天中断后任务继续运行。任务持有部署锁，
先重验制品、备份时效/摘要、配置和线上基线，再记录服务原状态、暂停直连调用方、关闭入口。
账号/用户并发与实际 TCP 连接连续归零后才停止旧应用；默认最多等 8 秒，排不空则恢复旧入口和
原来运行的服务，结果为 `DEFERRED`。排空窗口不包括前后检查，不是总维护时长上限。

仅执行应用的 `stop -t -1` 与 `up -d --no-deps --no-build --pull never`，不运行整套 `down`。
不会给 Docker 设置强杀倒计时，但应用自身仍有关闭超时，所以排空和停止日志必须同时检查；
停止结果未知、强制关闭或清理不完整均不能继续换候选。
应用、插件、入口资源、配置、迁移以及数据库/Redis **ID 和启动时间**通过后才开放公网并复验，
随后恢复原本运行的直连服务。所有 HTTP 检查统一使用普通 curl 与默认 TLS 信任，不加 `-k`。

| 最终状态 | 含义与下一步 |
| --- | --- |
| `ACCEPTED` | 服务器侧自动验收及服务恢复成功；再做外部正常 TLS/业务核验，更新原部署记录 |
| `DEFERRED` | 旧应用未停，忙请求使本次切换延后；另选低峰重新准备，不重放此尝试 |
| `RECOVERED` | 切换失败，已恢复此次操作开始前的应用并复验；不是新版本上线成功 |
| `ROLLED_BACK` | 明确发起的回退完成，已恢复旧应用并验收 |
| `PREFLIGHT_FAILED` / `LAUNCH_FAILED` | 检查或任务启动失败；查看日志和实际 unit 状态，不猜测已切换 |
| `NEEDS_ATTENTION` | 无法安全完成恢复；保留维护/待恢复标记，不强开入口、不自动恢复未知配套的直连服务 |

失败后仅在迁移、插件包/配置/绑定未变且原镜像匹配时自动恢复原应用，不修改或删除插件持久证据。
若曾开放候选公网，回退前重新排空；不能排空则保留维护等待处理。插件临时 `error` 状态不等于包或
配置变更，但恢复后仍必须通过真实健康检查。systemd `ExecStopPost` 处理主任务异常退出；
整机掉电、systemd 自身失效及无法确认的 Docker 操作不保证自动恢复，重启后先核对待恢复标记。

成功发布后需要回退时，在原准备材料仍有效且现场未改变的条件下运行：

```sh
python3 "$RELEASE/tools/fast_deploy.py" rollback --release "$RELEASE"
```

回退也要关闭入口、排空和独立验收，不是零中断。`activate/`、`rollback/` 分别保留
`state.json`、`task.log` 和停止日志，已有尝试不能重复执行；状态中记录 systemd unit 名。
失败需查 `journalctl -u <unit>`、私有 `command-errors.log` 与构建日志。不要手删 `.fast-deploy-pending` 或维护标记“修复”错误，
也不要在未对账状态直接调用内部 `_run` / `_recover` 命令。

### 本轮实现与验证边界

源码已新增 `/readyz`：初始化完成后检查数据库 Ping、Redis Ping 与已启用插件的权威绑定、
实际运行时和健康，采用短缓存与超时，不发收费模型请求；开始关闭时立即退出就绪状态。
原 `/health` 保留。插件 evidence 路径在宿主传参边界转为绝对路径，实际目录、0700 权限、
签名与持久保护不变；生产镜像现有 `PLUGINS_DATA_DIR` 无需移除。
真实隔离故障注入发现：数据库暂停时底层 Ping 可能不及时响应 context；就绪 HTTP 响应因此另有
两秒返回期限，未完成的依赖检查继续持锁，最多保留一个后台检查，不积压探测 goroutine。
新增不响应取消的依赖回归先复现、修复后定向 race 测试通过。最终 `5c28184c0` 镜像真实暂停
隔离 PostgreSQL、Redis 后，分别约 2.017、2.016 秒返回 503，恢复后重新就绪；插件进程暂停时
也返回 503，恢复后重新就绪。上述故障注入没有操作生产数据库、Redis 或插件进程。
隔离应用也必须配置独立且持久的加密密钥；临时默认密钥无法验证跨重启插件配置解密，
不能把这种夹具配置错误误记为宿主版本不兼容，更不能复制生产密钥到测试环境。

本轮本地已验证：

- 部署工具 40 项隔离单测，使用临时文件和模拟命令后端，不执行 Docker/systemd/生产请求。
  覆盖准备材料变更/过期、互斥、直连请求、公网 403、排空延后、回退前再次排空、插件/迁移变化、
  停机结果未知、原服务恢复、主任务退出收尾和拒绝重放；命令行帮助与 Python 语法检查通过。
- `go test ./internal/server ./internal/service ./cmd/server -count=1 -timeout=300s` 三包完整回归通过。
  随后插件就绪检查补上与配置写入/协调操作的互斥，同步失败测试先复现，再通过下述定向 race 回归。
- `go test -race ./internal/server ./internal/service ./cmd/server -run 'Test(Readiness|PluginReadiness|PluginEvidence|Shutdown)' -count=1 -timeout=180s` 通过。
- 内嵌资源、server、cmd/server 的 `-tags=embed` 测试，以及 Linux amd64 的
  `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -tags=embed ./cmd/server` 通过。
  Wire 生成文件保留同期模型广场修改，没有更改插件包、历史迁移或数据库/Redis 配置。

初次本地交付时开发机没有 Docker，当时未进行最终镜像、真实 Nginx/systemd 切换或生产演练，
未测得维护秒数。2026-10-20 用户随后确认以 `2c8d289cb8b13461979a79bc44a0f876bd70b9a0`
为基线，连同本期工具提交、推送，真实隔离验收通过后直接切换；含已提交的模型广场漏列修复。

- 验证原信任签名与完整安装包，保留数据库中实际使用的旧包，区分安装包和平台二进制摘要。

  与配对恢复不能被仅用于健康验收的版本条件阻断。签名、包摘要、配置、锁和回执检查仍保留。

| --- | --- |
| 新宿主已启动，插件安装或启用失败 | 区分原生替换工具是否已恢复旧包，再按实际状态恢复配套组合 |
| 新宿主、新插件健康，但公网验收失败 | 按预定流程核实入口；确需回退时先停用插件，再回退宿主和插件 |

### 独立任务与服务恢复

- 切换、条件回退及收尾在服务器独立任务内完成，不依赖聊天、模型响应或 SSH 连接。
  互斥与代次核对真实锁持有者；`flock --no-fork` 可使任务进程 PID 与锁记录一致。
- 暂停服务前持久记录其原状态；使用 `ExecStopPost` 等退出收尾机制覆盖成功和失败路径，
  仅恢复原本运行的服务，原本停止的不能自动启动。停止失败不得继续切换，恢复失败保留待恢复标记。
- 本机直连服务不受 Nginx 维护保护。只有应用与插件已恢复为可用配套状态才恢复其任务；
  回退中止、状态未知时保留维护和待恢复标记，报告需要处置，不能为了清除标记强行开放。

## 4. 最小变更切换与验收

1. 持有部署锁，启用维护入口，按已确认范围暂停直连调用方并确认停止，再等待账号/用户并发及实际应用连接排空；不能只看一个计数。
   等待应有明确上限和失败处理，不能为了赶进度强杀在途请求。具体标准见
   [生产可靠性](PRODUCTION_RELIABILITY.md)。
2. 正常停止旧应用，仅更新镜像绑定并重建应用。Compose 场景使用已核对的服务名和
   `up -d --no-deps sub2api`，不执行整套 `down`，尤其不能删除数据卷。
   数据库、Redis、连接池、插件配置及业务规则没有必要变更时保持原状。
   停机结果结合排空证据、容器状态/退出码、是否强杀及正常退出/清理日志判断；
   `context deadline exceeded` 单条日志不足以判定失败，退出码 0 也不足以证明全部清理完成。
   证据不足时先确认结果，不直接继续切换。
3. 检查启动/迁移结果、应用健康、制品身份、关键前端资源、管理员鉴权及相关插件。
   再核对数据库/Redis 容器身份及启动时间、配置差异和历史迁移 checksum；容器 ID 不变不证明未重启。
   区分程序文件摘要和运行进程映像摘要；读取 `/proc/1/exe` 被拒绝时如实标注未验证，不为取证增加容器权限。
4. 本机验收通过后恢复入口，用预先验证的客户端核对公网 HTTPS 健康、关键页面/资源及维护状态已解除；
   临时入口配置恢复原样，并从外部独立核对。公网检查未通过不能记作部署成功。
5. 按原状态恢复临时暂停的服务，核对其实际运行状态、原配置、维护标记及待恢复标记；
   收集独立任务退出日志和验收回执，全部满足后才记录最终成功。

### 失败与重试

- 公网 403 先按预定检查区分路径、代理/WAF、鉴权与应用错误。本次 `urllib` 与 `curl` 结果不同，
  但具体命中策略未查明，不能直接写成“WAF 误封”；不因验收失败修改 WAF 或关闭 TLS 验证。
  本机证书检查失败时，另从外部以正常 TLS 核对公网。
- 在预定时限内无法确认时，保留证据并按事先确认的兼容回退方案恢复服务，不在维护窗口临时开发
  或连续试切。无法安全回退则保持维护，记录当前宿主、插件和未完成操作，说明阻塞与恢复路径。
- 每次重试前归档上一尝试的脚本、日志、回执和结果，修正问题后重新测试、预检，核对旧任务及锁已结束。
  不直接重放历史启动命令，也不以最后成功覆盖前几次失败。
- 成功的 `systemd` 临时 unit 可能自动卸载；`LoadState=not-found` 既不证明失败，也不证明成功。
  结合 journal、最终验收回执、维护解除及服务恢复状态判断，不能只看 `systemctl show` 的默认退出字段。

**回退应用不会撤销已执行迁移。** 即使失败原因只是验收脚本缺失，新程序也可能已经执行 SQL。
回退后应核对实际数据库状态，不能据“恢复旧镜像”断言数据库未变。默认不恢复旧整库覆盖
上线后的业务数据；若旧程序不兼容新结构，应另行处理，不能盲目切回。
