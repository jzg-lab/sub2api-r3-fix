# 合并与部署更新指南

目标：提前准备新镜像及验收、回退材料，通过页面按钮进行同机双实例交接；
共用原数据库和 Redis，先暂停插件/任务，再切流量，最后恢复，不改插件包及缓存格式。
用户要求尽量不动现有环境，但必要的备份、兼容检查和迁移不能省略。
本指南长期维护；每次出现新的返工原因，都把预防措施补到这里，不另建日期版指南。

## 适用范围与记录入口

- 合并范围、个人要求和授权以 [产品规则](upstream-integration-policy.md) 及用户最新答复为准。
  已授权的事项直接执行，不重复询问；新冲突或超出范围的操作先沟通。
- 实现和回归入口见 [当前实现](local-customizations.md)；来源及合并历史写入
  [版本记录](upstream-sync-state.md)，当前线上身份和回退资源写入 [部署状态](deployment-state.md)。
- 本指南用于已有服务更新。不要对现网重新执行初始化安装脚本或覆盖 `.env`、Compose、密钥。
  单服务器更新不等于正式多平台 Release；后者另遵守 [发布要求](../RELEASE-POLICY.md)。

## 后续如何发起部署

用户最新纠正：**第二期就是页面部署按钮，不是要求用户照文档执行 SSH 命令。**
日常操作固定为：点击管理员版本入口 → 查看候选并点“准备更新” → 等待自动构建、隔离验收和备份 →
点“确认上线”并完成二次验证 → 页面显示最终结果。准备不切换，确认后服务器独立执行，
不依赖 AI、聊天、浏览器或 SSH 持续在线。

按钮、受控接口、独立准备任务和通用隔离验收已在本地实现，尚未安装到生产。
首次接入需要一次专项安装与验收，见[二期接入](#一次性接入与候选发布)。
[终端操作速查](#终端操作速查)保留为维护者排障/恢复入口，不再作为二期用户交付目标。
历史“终端先行”的表述是实施范围理解偏差，不是用户放弃按钮的授权。

- 新候选必须是已推送到本项目 GitHub、已审核的**完整提交 SHA**；不跟随可能变化的 `main`。
- 服务器源码同步命令见第 2 节；它只更新源码，不会部署或重启。代码已合并推送时，按第 2–5 节完成部署核对、准备、切换和验收；需要合并时才执行第 1 节。
- 迁移或数据影响超出已确认范围时，先说明具体影响再决定是否继续；否则按清单完成切换前检查。
- 用户明确要求切换前停住时，只完成构建、签名、备份、脚本和只读检查；不得启动维护、停用插件或
  创建会执行实际切换的任务。聊天自身经过待更新网关时，将切换与条件回退准备为服务器独立
  `systemd` 任务，明确日志和结果路径；等待用户继续后启动，不能依赖后续模型回复完成恢复。
  独立任务解决的是控制连接中断后的继续执行，不代表零停机，也不保证所有故障都能自动回退。

## 终端操作速查

### 准备者交付什么

每次切换前，准备者按[一期准备阶段](#准备阶段服务继续运行)交付一份简短清单：

| 必填项 | 要求 |
| --- | --- |
| 目标与基线 | 更新内容、完整新旧 SHA、候选镜像 ID；版本显示不能代替制品身份 |
| 更新类型 | 普通或专项；说明数据、配置、插件及回退兼容结论，未知项不得当作普通更新 |
| 发布目录 | 本次全新 `RELEASE` 绝对路径，0700；有 `prepared.json` 和封存的 `tools/fast_deploy.py` |
| 验收与备份 | 六项真实回执、受影响业务回归结果、备份完成时间及到期时间；不是 `not_run` 模板 |
| 操作边界 | 本次尚无 `activate/`；只切应用，短维护，排不空则延后；回退的目标与限制 |

没有这份交付或任一项未完成，停在准备阶段。不要直接 `git pull` 后重建生产容器。
此清单是给人确认的摘要，不能替代工具对回执、摘要和现场的正式检查。

### 用户确认和切换

在自己的终端登录服务器；`account-manager` 是当前电脑已经配置的 SSH 别名，
另一台电脑需先配置正常 SSH 登录，不要把生产凭据写进仓库。

```sh
ssh account-manager
```

下面的命令均在**服务器**执行。输入准备者给出的本次目录，不使用本文历史发布目录做新切换。
各步骤分开运行；报错即停，不连续粘贴准备、切换、回退三组命令。

```sh
printf '输入本次已准备的发布目录绝对路径：'
read -r RELEASE
python3 "${RELEASE:?}/tools/fast_deploy.py" status --release "$RELEASE"
```

核对目标 SHA/镜像与交付一致、备份未到期、没有该目录的既有 `activate` 尝试，
并确认可以开始短维护。**只有下一条命令会申请正式切换**：

```sh
python3 "${RELEASE:?}/tools/fast_deploy.py" activate --release "$RELEASE"
```

它返回 systemd unit 名及状态文件路径，表示任务已提交，**不是上线成功**。
如果连接中断，重新登录、重新输入同一个 `RELEASE`，只执行 `status`；不要再次 `activate`。

```sh
python3 "${RELEASE:?}/tools/fast_deploy.py" status --release "$RELEASE"
tail -n 60 "${RELEASE:?}/activate/task.log"
```

`QUEUED`、`PAUSING`、`DRAINING`、`STARTING`、`PUBLIC_VERIFY` 等是过程状态。
最终结果按下方[状态表](#批准后的切换与回退)处理：`ACCEPTED` 才是本次上线成功，
`DEFERRED` 是延后，`RECOVERED` 是回到此次操作前版本，不是更新完成。
非终态长时间不变、命令报错或 `NEEDS_ATTENTION` 时，查看状态中的 unit：

```sh
printf '输入状态文件中的 systemd unit 名：'
read -r UNIT
systemctl show "${UNIT:?}" --property=LoadState,ActiveState,SubState,Result
journalctl -u "${UNIT:?}" -n 80 --no-pager
```

不要杀任务、删维护标记或反复重试。正常结束的临时 unit 可能已被卸载，持久回执和日志仍在
`$RELEASE/activate/`；unit 消失本身不证明成功或失败。分享日志前去掉凭据和客户信息。

### 状态、验收和回退

- 服务器当前旧工具的 `PREPARED source=...` 只表示磁盘上存在准备记录，**不检查备份过期、
  线上健康或是否已部署过**；即使下面已有 `ACCEPTED`，第一行仍会是 `PREPARED`。
- 本地状态提示修正后改为 `PREPARATION_SNAPSHOT`、`BACKUP_WINDOW=CURRENT/EXPIRED/CLOCK_INVALID`
  和 UTC `expires_at`。`CURRENT` 只说明时间窗口尚在，不说明摘要、配置或现场仍通过；
  `LIVE_STATE_NOT_CHECKED` 明示这是只读快照。正式任务始终重做完整检查。
  此修正尚未安装到服务器，不能覆盖历史发布目录里的封存工具。
- `EXPIRED` 不表示此前成功部署失效，只表示这份备份不能再用于新的切换/回退。
  已有尝试不得重放；过期、延后或失败后重新评估并准备新目录，不能改时间戳续期。

`ACCEPTED` 后，在**自己的电脑**用正常 TLS 核对两个正式入口；以下不含管理员凭据：

```sh
curl -q --fail --show-error --silent --max-time 10 https://ciyuan.fast/readyz
curl -q --fail --show-error --silent --max-time 10 https://api.ciyuan.fast/readyz
```

再打开主站与模型广场，核对版本及本次改动涉及的正常业务；健康接口通过不代表价格、路由等
所有业务正确。记录通过、失败、未测项及发布目录到[部署状态](deployment-state.md)。
不为验收自动发起收费模型调用或真实充值。

只有本次 `activate` 为 `ACCEPTED`、备份未过期、现场仍兼容，且你明确决定回退时，
在服务器同一个 `RELEASE` 下运行：

```sh
python3 "${RELEASE:?}/tools/fast_deploy.py" rollback --release "$RELEASE"
python3 "${RELEASE:?}/tools/fast_deploy.py" status --release "$RELEASE"
```

回退也有短维护；成功结果为 `ROLLED_BACK`，日志在 `$RELEASE/rollback/`。
过期或现场变化时交维护者重新评估，不直接改 `.env`、下载旧包或恢复整库。

### 固定流程与边界

用户操作固定为：**检查版本 → 查看更新内容并准备 → 准备完成后确认上线 → 查看结果**。
检查与准备不切换服务；推送 GitHub 不自动上线。更新来源仅为本项目已审核的候选版本，
不自动合并老板版或官方版，也不直接下载官方程序替换本地定制。

| 通道 | 准入与处理 |
| --- | --- |
| 普通更新 | 无新增或改写迁移、无启动期数据转换；插件、持久状态格式、配置及运行环境兼容；有对应审核结论，规定测试和新旧版本往返验证通过。只替换应用镜像 |
| 专项更新 | 数据库结构/数据转换、插件包或协议、运行依赖、Docker/浏览器环境、密钥/配置格式、部署工具或入口配置自身变化。页面列出影响和阻断原因，禁止普通上线；另行评估、确认和实施 |
| 无法判断 | 兼容信息、来源或验证证据缺失时转专项待评估，不凭“只改代码”或文件路径未命中就放行 |

无迁移 SQL 不等于数据兼容：代码也可能在启动或业务写入时改变数据含义、缓存格式或插件状态。
维护者应随候选记录数据/配置/插件影响和回退条件，自动检查负责核对事实及阻断项，不能代替语义审核。
普通更新“全程无需 AI”指已审核代码的准备和上线，不包括自动判断任意新代码是否正确。

普通更新不重启或升级 PostgreSQL、Redis，不删除卷、不恢复整库，不重置业务配置、密钥、
账号、插件绑定或持久保护；只允许按一期工具约束更新 `.env` 的应用镜像绑定。
“不动数据库”指不做部署迁移、清理或覆盖，正常业务写入照常继续。

### 自动准备与页面流程

以下流程已有本地实现；生产启用和首次完整普通更新验收仍待专项接入。

1. **选择候选。** 从受控的本项目候选清单取得版本、更新摘要、官方同步基线、完整 SHA、
   兼容声明和审核依据；与实际线上基线比较整个差异。候选声明不能自行覆盖检查结果。
   固定目标后出现新提交不自动换目标；线上基线变化则重新评估。
2. **准备与验证。** 独立任务检查磁盘和可用内存，再从固定归档构建不可变镜像；
   发布者先完成本次业务回归并在候选审核中记录，自动任务执行最终镜像隔离验收和兼容往返验证，
   生成真实日志、摘要及结果。编译或启动成功不代替业务语义回归。
   复用一期 `artifact.json` 和回执字段，不把 `evidence-template` 的 `not_run` 批量改成通过。
   生产数据库、Redis 和插件进程不参与故障注入，测试不发起未授权的真实供应商调用。
   同一候选因备份过期、排空延后或备份阶段失败重新准备时，可复用最近一次封存的镜像与隔离验收。
   候选、构建工具/镜像、线上程序/数据服务身份、迁移、配置、插件、入口或调用方材料变化，
   或日志缺失/摘要不符、镜像绑定变化，均不复用；不扫描任意历史版本，也不改写历史验收。
   复用只省去构建及隔离往返，仍创建新任务/发布目录，重新做现场预检和备份，等待新的上线确认。
3. **等待确认。** 核验入口、直连调用方、插件及配置，完成备份和 `prepare` 后，展示固定目标、
   变更、检查结果、备份有效期和维护影响。此时旧版继续服务；用户未确认不得暂停后台或关闭入口。
   备份默认两小时有效，过期重新准备；旧确认不能用于身份或现场已变化的新尝试。
4. **独立切换。** 点击确认后，由服务器 systemd 任务持锁重验材料，暂停配置中已批准的直连服务，
   开维护、排空，再只替换应用容器。账号管理正式版及试运行版均按原状态暂停/恢复，
   不因此删除、升级或扩大其他服务的操作范围。忙请求排不空就延后，不能强杀或循环制造维护窗口。
5. **验收与记录。** 自动检查就绪、制品身份、前端、插件、管理员正常鉴权及所有正式公网入口；
   当前范围为 `ciyuan.fast` 和 `api.ciyuan.fast`，不含已停用的 cn/hk 域名。
   恢复原本运行的直连服务，保存结果、耗时和日志；网页重连后读取任务结果，不以 HTTP 断连
   或倒计时结束判定成功。服务器自访公网与独立外部验收分别标记，未运行的业务检查不写通过。

准备预计 10–30 分钟，仅为待实测估计，随缓存、资源、测试及备份大小变化；准备期旧版继续运行。
复用验收后主要耗时为现场检查与新备份，尚无本轮真实服务器计时，不给固定分钟承诺。
一期一次成功切换实测独立任务约 10 秒、公网维护约 4 秒，不能保证下次固定几秒或绝对零中断。

### 异常与权限

- 构建、测试或备份失败停在准备阶段，旧服务不变；测试失败不自动跳过，也不自动换另一个版本。
- 重复点击、并发管理员和命令行共用部署互斥与任务身份，不能启动第二次切换；刷新或关闭页面、
  应用容器重启均不终止独立准备/切换任务。任务状态存仓库外私有目录，不为按钮新增业务库迁移。
- 排空失败沿用 `DEFERRED`，恢复旧入口及原服务；新的尝试重新准备，不能重放或自动反复重试。
  候选失败仅在一期兼容条件和实际健康验收满足时记为 `RECOVERED`，不能显示“升级成功”。
- 最近任务和可回退的已上线发布分别持久化。新的准备失败不会覆盖上一成功发布的回退入口；
  新任务执行中或结果未知时不提供回退。新发布成功即取代旧回退记录，不可跨过它回退更早版本；
  有效期、兼容性及实际镜像仍由封存切换器重验，不能仅凭页面有按钮认定可回退。
- 无法确认停止结果、状态兼容或恢复成功时沿用 `NEEDS_ATTENTION`，保留必要维护和待恢复标记，
  提示维护者处理；不靠恢复数据库备份掩盖问题，避免丢失准备以后发生的正常业务写入。
- 沿用管理员鉴权、已有敏感操作验证及审计。应用仅能向受控本机执行入口提交允许的发布 ID 和动作；
  执行端重新核验来源、路径、制品、权限和状态。不向应用容器挂 Docker socket、开放任意 root shell，
  不接受网页传入任意命令、下载 URL、服务名或文件路径；私密日志、凭据和备份不返回浏览器。
- 执行器由独立受控目录维护，不在普通更新中执行候选提交带来的部署脚本；工具自身升级走专项。
  整机掉电或系统服务失效仍可能需人工恢复，页面不可用时保留一期命令行状态/恢复入口。

### 一次性接入与候选发布

此节由维护者在首次启用时执行，不是每次要求用户手工准备。首次接入改变部署工具、环境变量和
Compose 挂载，必须走专项；不能把本轮实现本身伪装成普通应用更新。

- 安装同一已审核版本的 `managed_deploy.py`、`verify_fast_release.py`、`build_fast_release.py`、
  `fast_deploy.py`、`handoff_deploy.py`、`FastRuntime.Dockerfile` 到 `/opt/sub2api-control/tools/`，仅 root 可写。
  主控制器和恢复计时器统一运行该目录内的 `managed_deploy.py`，读取
  `/opt/sub2api-control/config.json`；不另外创建 `controller.json` 或复制根目录脚本。
  私有目录 0700、JSON/凭据 0600，参考 `managed-deploy.example.json`；沿用已验收的一期配置，
  两个正式域名和两套直连后台的暂停范围不扩大。不覆盖历史发布目录的封存工具。
- 建立一次性的 `verification-manifest.json`：原签名插件包、原公钥信任、当前插件配置副本、
  Nginx 已通过的隔离验收日志均记录私有绝对路径及 SHA-256；另固定 `production_plugins`、
  `nginx_sha256`、`caller_inventory_sha256` 和相关配置/服务文件 `inventory_files`。
  值分别来自一期 `plugin_contract(host.plugins())`、`nginx_hash()`、`caller_inventory(host)`
  及文件摘要，不手工填写“通过”。插件包须与线上包摘要相同；配置/调用方/入口变化时重新审核，
  不自动接受新值。当前通用夹具只支持一个已启用的已批准插件。
- 安装 `sub2api-deployment.service`。Unix socket 由 root 创建，0660，仅应用组可连接；
  应用只读挂载整个 `/run/sub2api-deployment` 目录，并设置
  `MANAGED_DEPLOY_SOCKET=/run/sub2api-deployment/control.sock`。不挂 Docker socket、私有凭据或备份。
  单文件 socket 不能作为挂载对象；目录也必须设 `RuntimeDirectoryPreserve=yes`，防止 systemd
  停止/重启时删除目录、使运行中容器仍挂载旧目录 inode。整机重启后目录/服务应先于应用建立。
  控制器用独立生命周期锁禁止多实例，仅清理确认已拒绝连接的自有遗留 socket，非 socket、
  活跃监听或无法判断的路径均拒绝替换。管理员需启用既有 TOTP 二次验证。
  首次接入需在 Linux 的真实挂载中测试 crash/restart 和 stop/start，不能只重新实例化 Python 对象。
- 配置 `github_catalog=true`，候选从本项目 `main/.github/deployment-candidates.json` 取得；
  缓存 5 分钟，刷新/准备/确认可强制重查。候选 SHA 固定，拉取清单不等于部署 main。
  清单当前为空，尚无首个可部署候选；没有伪造发布序号或将历史版本重命名。
- 同时安装并启动 `sub2api-build.slice`，默认构建容器共用 2 CPU、6GiB 内存、禁止 swap，降低 CPU/IO 权重。
  受管构建固定使用本机默认 Docker/buildx 的 `docker` 驱动及 cgroup v2；两次 build 都传入
  `--cgroup-parent /sub2api.slice/sub2api-build.slice`，准备时读取实际 cgroup 限额，不满足则阻断。
  不用只限制 Python 客户端的 `MemoryMax` 冒充 Docker 编译容器限额，也不换成无法直接读取本机
  运行时镜像的独立 docker-container 构建器。首次接入仍须核对真实 RUN 进程处于该 cgroup 后代，
  并采样 `cpu.stat` / `memory.peak`；本地已有隔离 Docker，尚未完成此 systemd/cgroup 验收。
- 2026-10-23 首次服务器构建在预算预检即停止：目标机 buildx v0.34.0 的 `inspect` 不支持
  `--format`。预算检查改用 `buildx ls --format '{{json .}}'` 核对 `default` 的 `docker` 驱动；
  部署前在目标机实跑该预检，不能只依赖开发机的 CLI 行为或单测替身。
- 同次首次隔离验收发现 `systemctl list-unit-files` 还列出由验证任务自身创建的 transient unit；
  清单摘要须排除这些临时 unit，仍核对持久 service/timer 和两套获批后台的实际 unit 定义，
  否则任务刚启动就会误判“调用方变化”并永久阻断按钮准备。
- 上线前确认镜像/备份保留策略。目前空闲资源门槛默认 20GiB 磁盘、
  8GiB 内存；隔离应用/数据库/Redis 分别限定 4GiB/1GiB/256MiB 和 2/1/1 CPU。
  编译容器限额不包含 Docker 守护进程导出镜像、宿主归档和数据库备份的全部开销，不能承诺零影响。
  不自动删镜像、备份或历史失败证据；空间不足先阻断。维护者清理前必须保留当前运行、有效回退、
  最近可复用验收和仍被现有配置引用的工具/凭据目录，不能全局 `docker system prune`。

### 可复用验收经验

- 插件配置 PUT 返回原始 JSON，与登录等接口的 `{code,data}` 包装不同；解析器显式区分，
  不用同一个变量同时表示“原始模式”开关和响应字节。该错误已在真实夹具复现并增加回归。
- 入口脚本会降权，`docker exec id -u` 仍可能报告镜像默认 root；检查实际应用 PID 1 的
  `/proc/1/status` UID，不把 exec 子进程身份当作应用身份，也不因此提高应用权限。
- 故障注入只暂停隔离数据库/Redis/插件；夹具无生产数据挂载、无发布端口、无业务账号、
  使用 internal 网络。清理失败或任务中断保持 `NEEDS_ATTENTION`，不继续准备生产切换。
- 页面确认绑定任务 ID 和目标 SHA，备份到期或另一管理员替换任务时关闭旧确认。
  网络丢失只查询持久状态，不自动重发变更；确认弹窗先关闭，再交给现有二次验证弹窗。

### 交付验收

第二期完整交付前，必须让用户在页面上、不依赖聊天地从一个已审核的固定新 SHA 完成准备、
确认、断线后查询与外部验收；新候选必须生成自己的真实隔离证据，不能靠维护者临时改旧脚本路径。
本地接口/页面回归和历史制品隔离往返已通过，**尚未完成生产按钮端到端验收**。完整交付条件：

- 普通候选从检查到结果可由管理员在页面完成；中途关闭网页、断开 SSH/聊天不影响任务及条件恢复。
- 有迁移、依赖/插件或配置变化、来源不符、审核/测试缺失、备份过期、线上基线漂移时不能点击上线；
  直接调用旧接口同样不能绕过受管检查。版本排序覆盖自有版本递增、官方基线变化和历史版本识别。
- 隔离环境覆盖准备失败、并发/重复点击、排空延后、就绪超时、主任务异常退出、条件回退及不能回退；
  页面正确区分成功、延后、恢复旧版和需人工处理，回退不是任意选择一个旧版本下载。
- 生产演练记录应用/插件身份、维护时长、数据库/Redis ID 与启动时间、迁移清单、业务配置及原服务
  恢复情况。自动记录不能代替未执行的浏览器业务核验；通过、失败、未测项分别保留。

### 双实例追加实施

**当前方案：双应用、单插件/后台所有者。** 用户最后确认采用共库交接，取代稍早的单实例替换。
不恢复插件共享 Cookie、缓存迁移、新签名或长时间双活退休协议；原签名包及业务数据保持不变。

普通流程固定为：**固定 SHA → 构建/隔离验证 → 新备份 → 人工确认 →
新实例待命启动 → 暂停直连后台/短维护 → 旧请求和计费排空 → 停旧实例插件/任务 →
新实例接流量 → 恢复原插件/任务 → 入口验收 → 恢复原直连后台**。

- 新实例在旧实例服务期间完成启动；共用现有 PostgreSQL/Redis，不复制业务库、不重启数据服务。
  受管启动仅核验已执行迁移，不创建表、不生成密钥、不做初始化设置迁移或下载价格文件。
- 插件暂停通过本机私有 Unix socket 控制宿主进程，不调用 Disable/Enable 修改数据库绑定。
  同一个共享文件锁保证只有一个实例有权接流量、启动插件及自主后台任务。
- 旧实例保留为待命。确认回退时先重新启动待命槽以刷新内存缓存，再按相同顺序反向交接；
  切换过程中失败则优先使用尚未退休的旧进程恢复。回退绝不恢复整库，保留期间新增的交易。
- 入口切换由固定 Nginx upstream include 完成；主站、API 和原 `127.0.0.1:8080` 直连入口必须
  指向同一个 upstream。新旧应用仅绑定独立回环端口；实际响应的启动 ID 必须与目标进程一致。
- Nginx 配置摘要只归一化该 include 的二选一内容；其他配置、迁移或插件契约变化仍阻断切换/回退。
  `single` 历史回执不能当成 `handoff` 证据。双实例准备额外要求真实 `shared_database_handoff` 回执。
- 待命启动失败不关入口；排空超时取消本次更新并恢复旧服务；切流后失败反向交接。
  若候选无法安全排空、数据库故障或归属无法确认，保持维护并报 `NEEDS_ATTENTION`，不能保证任意故障秒退。

本地实现入口：`handoff_deploy.py`、`server/handoff.go`、后台任务 admission gate、受管启动核验。
一期构建/备份/私有凭据/封存/systemd 独立任务继续复用；一期单实例执行器只用于旧安装维护及首次专项接入。

#### 首次双实例接入

这不是日常按钮自动修改的内容，且本轮未执行生产安装：

1. 冻结已验证的本项目版本；当前线上旧二进制没有交接控制，首次需短维护升级并明确初始化活跃槽。
2. 在原私有配置中显式设置 `mode: handoff`，增加 `handoff.slots.blue/green`：各自的
   `compose_file/env_file/app_service/app_container/app_port/local_url/control_socket`；增加
   `handoff.upstream_file`、`handoff.pricing_file`（现有价格文件的主机路径）及
   `handoff.stable_url`（固定原 `http://127.0.0.1:8080`）。
3. 两槽挂载同一现有 `/app/data`，使用相同数据库、Redis、JWT、TOTP、插件配置；设置各自
   `DEPLOYMENT_SOCKET=/app/data/.handoff/<槽>.sock` 和相同
   `DEPLOYMENT_OWNER_LOCK=/app/data/.handoff/owner.lock`。预建私有目录、`owner.lock`、
   两个 `<槽>.sock.lock`，归运行 UID 所有，目录 0700/文件 0600；不要用临时 inode 替换锁文件。
4. 安装并验收稳定 Nginx 入口、两个固定回环端口及所有维护门禁。upstream include 仅允许一行
   `server 127.0.0.1:<槽端口>;`。两个获批账号后台仍按原活跃状态暂停/恢复，不删除或升级。
5. 安装原控制器、socket 挂载及构建限额，同时安装 `sub2api-handoff-reconcile.service/.timer`。
   首次初始化私有 `handoff-active.json`（已核实的槽及制品身份）；计时器只恢复已选定版本或未完成任务，
   不擅自挑新版本。验证 systemd 中断、容器重启及宿主重启恢复后才开放按钮。
6. 用最终 Linux/amd64 镜像及现有原签名插件做共库往返、真实入口、计费及浏览器按钮验收；
   本机无插件/零账号测试和历史通过不能替代这些验收。

切流后保留 10 秒连续验收，通过后才记为成功；期间失败反向交接。原实例若遇到价格/设置后台更新，
先在维护内重启原槽刷新缓存再接管，避免用旧内存配置计费；不能把这一分支承诺成零秒回退。

恢复重入须在旧槽刷新并核验配置未漂移后、接流量前，将配置摘要和启动 ID 写入现有尝试记录。
执行器此后退出，重试复用该已核验进程，不再次重建正在接流量的槽；配置或启动身份再次改变时，
先安全排空、暂停，再刷新待命槽。不能删除 `cannot replace a serving slot` 等保护来强行继续。

主应用验收、解除配置冻结并保存成功状态后，再恢复附属直连后台。原本活跃的后台名单先持久保存
在 `handoff-active.json` 的 `pending_services` 中；后台启动失败只记录日志并由恢复计时器重试，
不把已验收主站回退或重新关进维护。原本关闭的服务不启动，成功后清除待恢复名单；重试中退出或
保存失败允许幂等重试。页面显示附属后台待恢复提示，完成前阻断下一次切换，避免覆盖恢复责任。

公开 `/readyz` 只在 `active` 且完整依赖检查通过时成功；待命、排空及 `serving_paused` 均为 503，
插件恢复持续失败不能冒充完整就绪。切流前通过私有 Unix `/status` 的 `core_ready` 核验核心依赖，
Nginx 切换验证 `/health` 返回的启动身份；切流后才恢复插件并执行完整就绪验收，顺序不变。

2026-10-23 复查修正：计费用量队列和缓存写入队列与异步生产者共用在途计数，子任务在父任务
退出前登记；不能先看到空队列、再等异步任务结束就宣布排空。全部续作完成后主动刷新最后使用
时间，不再为默认 10 秒批处理周期额外维持维护；刷新失败保留更新并取消交接，不丢数据。

恢复计时器仅在完整验收且解除配置冻结后保存本次启动 ID，半途失败时即使已进入 `active`
也要重试收尾。正常 5 秒巡检只检查容器镜像、启动 ID、源码及核心依赖；新启动或交接仍完整
校验二进制、插件和入口资源。切流观察期保留就绪和入口身份探测，不循环下载全部资源；开放
入口由切流方法负责，调用方不重复执行。

未完成部署的恢复仅可忽略数据容器启动时间变化：容器 ID、镜像、数据挂载、PostgreSQL 集群
标识及数据库 OID/名称/目录必须与准备记录相同，迁移、配置、插件契约检查仍保留。正常切换
预检仍严格拒绝数据容器重启。数据卷替换、数据库重建、身份不明或旧回执缺少持久身份信息时
保留维护并人工处理；不删除检查来强行恢复，也不恢复整库。该检查要求部署数据库用户能只读
查询 `pg_control_system()`；权限不足会阻断准备，不由工具自动提权。

新增可复用经验：Wire 结构新增依赖字段时必须同步 `wire.Struct` 的字段清单，否则生成代码能编译但值为 nil；
备用启动审计须覆盖启动一次性回填及队列消费者，不能只暂停 cron。计费写入继续完成，不能随定时任务一起丢弃。
任务入队前若已占用去重/运行标记，释放责任必须覆盖待命门禁的提前返回；不能只在真正执行
业务分支后释放。渠道监控曾因此在首次待命跳过后永久不再运行，现由真实 `fire` 路径回归。
交接排空还须覆盖已接收的审核/邮件队列以及脱离父任务的有限子协程；单独有 `Pending` 或
进程退出 `Stop` 不代表交接路径会等待。入队/启动前登记，拒绝、配置跳过和退出成对释放，
常驻 worker 不整体计数，不以丢弃待处理审核任务换取切换成功。手动消费队列的测试也须收尾，
用重复组合回归检查跨用例计数泄漏。
全包归零验收须在所有测试结束后执行，并覆盖业务定时释放的正常等待；计费探针的分钟周期尾
锁释放不能仅凭 5 秒未归零判为泄漏。部署仍使用配置的 `drain_seconds`（当前示例 8 秒、允许
1–30 秒），超时取消更新并恢复旧服务，不把私有接口 120 秒上限或测试等待预算当成维护承诺。
Unix 锁实现按平台隔离，Windows 交接明确报不支持，不删除原发布目标或放宽锁保护。
前端源码冻结后正常构建并同步内嵌资源，再运行 `go test -tags=embed ./internal/web`；
只验证开发页面不能证明直接 embed 构建包含新按钮。
工具安装清单和两个 systemd 入口的路径一致性由 `deploy/tests/test_deployment_installation.py` 回归；
不能把脚本单测通过当作实际 systemd 安装/重启验收。

## 第一期工具与操作流程

本期提供 [构建工具](../deploy/build_fast_release.py)、[部署工具](../deploy/fast_deploy.py)、
[运行镜像模板](../deploy/FastRuntime.Dockerfile)、[私有配置示例](../deploy/fast-deploy.example.json)
及 [Nginx 维护入口示例](../deploy/fast-deploy-nginx.conf.example)。只支持本机 Linux Docker Compose、
单应用实例和 systemd；不做通用集群发布平台，不修改业务配置、升级插件或恢复整库。

### 首次接入条件

以下是正式使用工具前的一次性准备；实际接入结果以部署状态中的当次证据为准：

- 提交并按授权推送本期源码后，固定完整 SHA。候选必须包含 `/readyz`；未提交工作区不能作为构建输入。
- 目标机器需要 Python 3.9+、Docker/Compose v2、使用本机镜像的 Docker 构建器、Git、tar、curl、
  Nginx 与支持 `StandardOutput=append:` / `Type=exec` 的 systemd。运维工具按 root 身份执行。
  构建须核对磁盘、内存及资源限额；本工具不自动决定生产机器可以承受的构建负载。
- 在**所有实际接入的 Nginx server 块**正确位置安装维护文件判断，核对已有 rewrite、重定向与缓存配置，
  单独批准后 `nginx -t`、reload 并演练。维护由文件存在与否控制，正常更新无需反复改写/reload Nginx。
  示例不能不经审查整段覆盖现有配置；确认 Nginx worker 可访问维护标记的父目录。
- 将实际所有 HTTPS 入口填入 `public_urls`；示例只有主域名，不代表已覆盖聊天专用域名或内网入口。
  准备检查 `/__deploy_guard` 返回 204；真正切换关闭入口后要求各入口返回 503，否则不停止旧应用。
  受 IP 限制的 HTTP 直连入口使用 `guard_checks` 检查已有路径，正常保持 403、维护时 503，
  不添加绕过原 ACL 的可访问业务入口；这里只允许回环地址。旧域名不可达时先确认使用范围。
- 盘点能绕过 Nginx 的服务、timer、内网直连及自动重启来源。只在用户批准范围内填写 `pause_services`，
  不允许外部直接打到未受控的应用端口。持续直连、长 WebSocket 或 keepalive 可能使本次更新延后，
  不能将三个零计数样本解释为能够阻止所有未知调用方。
  被暂停的服务必须有可恢复的 unit 定义；一次性 `systemd-run` 临时服务停止后可能被卸载。
  隔离演练的模拟调用方也应使用持久的服务定义，不把临时服务消失误判为生产恢复逻辑故障。
- `.env` 必须有且仅有一条普通 `SUB2API_IMAGE=镜像`，Compose 应用确实使用它。凭据、配置、
  回执、镜像清单和备份放仓库外的 0700 私有目录；`admin_header_file` 为 0600 文件，内容为正常
  管理员 API Key 的 `x-api-key: ...` 请求头。工具只用于正常只读管理接口，不提供鉴权或二次验证绕过。
  运行容器的 Compose 配置 hash 必须与当前渲染结果一致；有未应用配置或 Compose 版本导致的
  hash 差异时先核查，不自动重建来消除差异。构建/备份目录没有自动清理，按保留策略人工回收。
- 生产旧版没有 `/readyz` 时，显式设 `previous_has_readyz=false`，旧版验收仍检查健康、制品、
  插件、管理员鉴权与前端；候选版一律要求就绪成功。之后部署应设为 `true`，不是自动降级为 `/health`。
  `migration_aliases` 示例只对应现有九条已核实的历史别名，须与当前迁移器对照，不能借此放行未执行迁移。

### 准备阶段：服务继续运行

本节由准备者操作。2026-10-20 已只读核实的现有工具及私有配置位置如下；这些路径依赖
历史构建/接入目录，尚无独立安装目录，清理旧材料时必须保留，迁移它们需单独核验。

```sh
TOOLS=/opt/sub2api-backups/releases/fast-build-083053ab2/source/deploy
PRIVATE_CONFIG=/opt/sub2api-backups/releases/fast-supply-083053ab2/production-config.json
```

`TOOLS` 使用已验收源码中的工具，不跟随拉取后的候选脚本变化。当前私有配置已包括主站、API、
两套获准临时暂停的账号后台及 `previous_has_readyz=true`；凭据仍在原 0600 私有文件内。
不要用仓库的 `fast-deploy.example.json` 覆盖它。本地这次状态提示修复尚未安装到该目录；
部署工具自身升级走专项接入，不修改已封存发布的脚本。实际路径及摘要见[部署状态](deployment-state.md#终端流程只读核验2026-10-20)。

以下变量均由当次核验确定；`NEW_SHA`、`OLD_SHA` 是完整提交，`OLD_IMAGE` 是已核对的运行镜像，
`NODE_IMAGE`、`GO_IMAGE` 必须带固定 `@sha256:...`。`BUILD`、`RELEASE` 是仓库外全新私有目录，
不要复用过去已尝试的发布目录。

```sh
python3 "${TOOLS:?}/build_fast_release.py" \
  --repo /opt/sub2api-source --output "$BUILD" \
  --commit "$NEW_SHA" --previous "$OLD_SHA" --runtime "$OLD_IMAGE" \
  --node-image "$NODE_IMAGE" --go-image "$GO_IMAGE"

install -d -m 700 "$RELEASE"
python3 "${TOOLS:?}/fast_deploy.py" evidence-template --release "$RELEASE" \
  --config "$PRIVATE_CONFIG" --artifact "$BUILD/artifact.json"
```

构建从 Git archive 取固定源码，不受脏工作区影响；提前构建内嵌前端和应用，运行相关后端测试，
在旧运行镜像上只替换程序及资源，保留浏览器、Node/Python、插件目录、用户与入口设置。
并行开发期间，定向回归也使用同一完整 SHA 的独立归档，不用可能继续变化的工作区作为发布证据。
准备中出现新的提交不自动更换本次目标；记录本次固定提交与后续尚未部署的改动。
Go 定向测试同时核对文件 build tag、用例名称和实际执行数；模型广场 handler 等测试需要
`-tags=unit`，部分价格回归名为 `TestListGroups_...`，不能仅凭包返回成功或 `no tests to run` 判定覆盖。
部署版本在源码 SemVer 后追加 `fast.<SHA>` 构建元数据，不能用 `deploy.<SHA>` 替代合法版本，
否则插件最低宿主版本检查会拒绝。Go 测试在挂载相同模块缓存的 BuildKit 阶段执行；缓存挂载不会
保留在 builder 镜像中，直接启动断网 builder 容器运行测试会因依赖缺失而失败。
完整后端测试还需要仓库 `deploy/client-identity` 资料及 `/usr/bin/true` 测试替身路径；仅在测试阶段
补齐，不能跳过失败测试或将测试依赖混入沿用的运行镜像。
迁移 SQL/迁移器、插件包/协议、Go 依赖、Dockerfile、浏览器/客户端运行资源变化会被拒绝，
进入专项流程。此静态检查不是兼容性证明，宿主业务行为仍须核验。构建不是正式五平台 Release。

`artifact.json` 记录新旧源码、镜像及运行基底 ID、二进制、前端资源摘要、迁移清单与构建输入。
`evidence-template` 只生成 **`not_run` 模板**，不会声称测试通过。对最终候选在隔离环境完成以下检查，
把实际日志保存在发布目录并记录 SHA-256，再将对应状态记为 `passed`：

| 回执检查项 | 必须记录的实际证据 |
| --- | --- |
| `runtime_uid_paths` | 最终镜像、实际 UID/工作目录、相对与绝对插件目录；不挂生产数据 |
| `plugin_rpc_existing_config` | 同签名插件包及现有配置副本的健康 RPC/Host HTTP 通道就绪；不冒充真实模型请求，保留原保护与信任 |
| `startup_readiness` | 隔离数据库/Redis 的启动和就绪；依赖或插件不可用时 503；前端资源一致 |
| `compatible_rollback` | 同插件、同结构的新旧宿主往返与失败分支，不能只验证新宿主可启动 |
| `direct_callers_inventory` | 已批准暂停的直连服务、timer/监督进程及端口暴露核对结果 |
| `nginx_guard` | 所有入口上的维护判断、正常 TLS、普通 curl 路径；首次接入的实际测试记录 |

回执绑定源码、基底、新镜像、程序、私有配置和实际插件清单。程序验证身份与日志摘要，
不自动证明日志中的结论；维护者必须检查真实执行结果，禁止手填假通过或拿旧镜像的回执替代。
真实供应商调用、压力测试及完整数据库恢复演练仍单独列明，不由这些检查冒充。

**历史脚本边界：** 服务器的 `fast-phase1-20261020/rehearse.py`、`production_prepare.py` 和
`retry_prepare.py` 是历史发布专用脚本，包含固定旧镜像、目录及夹具名，不是可重跑的通用入口。
不要对新候选执行这些旧脚本、覆盖旧 `lab`，或批量把 `not_run` 改成 `passed`。
本地二期已实现 `verify_fast_release.py` 参数化入口，生产尚未安装；手工维护时仍须真实执行并审核
上述检查，历史临时脚本只作证据保留，不直接复用于新候选。

```sh
python3 "${TOOLS:?}/fast_deploy.py" prepare --release "$RELEASE" \
  --config "$PRIVATE_CONFIG" --artifact "$BUILD/artifact.json"
python3 "$RELEASE/tools/fast_deploy.py" status --release "$RELEASE"
```

`prepare` 核对现有镜像/提交、Compose 对象与有效配置、历史迁移、插件、所有公网路径，
保存私有配置快照，执行 `pg_dump -Fc`、SHA-256 和同版本 `pg_restore --list` 检查。
同时冻结切换脚本与准备文件摘要。此阶段不关闭入口、不暂停服务、不重启应用，也不创建切换任务。
用户要求“切换前停住”时，到此为止。备份默认两小时过期，过期或材料变化须重新准备。
直接运行本节一期 `build` 和 `prepare` 命令仍是前台执行，并没有自动脱离 SSH；准备期间保持连接。
二期按钮通过独立 systemd 准备任务调用这些函数，不受页面或 SSH 断连影响。
意外断线后先查进程及材料，不并发重跑或删除已有目录；有不完整尝试时保留证据另建目录。
下文 `activate/rollback` 才由工具交给独立 systemd 任务运行。

### 批准后的切换与回退

```sh
python3 "$RELEASE/tools/fast_deploy.py" activate --release "$RELEASE"
python3 "$RELEASE/tools/fast_deploy.py" status --release "$RELEASE"
```

`activate` 只启动服务器独立 systemd 任务；SSH/聊天中断后任务继续运行。任务持有部署锁，
先重验制品、备份时效/摘要、配置和线上基线，再记录服务原状态、暂停直连调用方、关闭入口。
账号/用户并发与实际 TCP 连接连续归零后才停止旧应用；默认最多等 8 秒，排不空则恢复旧入口和
原来运行的服务，结果为 `DEFERRED`。排空窗口不包括前后检查，不是总维护时长上限。

仅执行应用的 `stop -t -1` 与 `up -d --no-deps --no-build --pull never`，不运行整套 `down`。
不会给 Docker 设置强杀倒计时，但应用自身仍有关闭超时，所以排空和停止日志必须同时检查；
停止结果未知、强制关闭或清理不完整均不能继续换候选。
应用、插件、入口资源、配置、迁移以及数据库/Redis **ID 和启动时间**通过后才开放公网并复验，
随后恢复原本运行的直连服务。所有 HTTP 检查统一使用普通 curl 与默认 TLS 信任，不加 `-k`。

| 最终状态 | 含义与下一步 |
| --- | --- |
| `ACCEPTED` | 服务器侧自动验收及服务恢复成功；再做外部正常 TLS/业务核验，更新原部署记录 |
| `DEFERRED` | 旧应用未停，忙请求使本次切换延后；另选低峰重新准备，不重放此尝试 |
| `RECOVERED` | 切换失败，已恢复此次操作开始前的应用并复验；不是新版本上线成功 |
| `ROLLED_BACK` | 明确发起的回退完成，已恢复旧应用并验收 |
| `PREFLIGHT_FAILED` / `LAUNCH_FAILED` | 检查或任务启动失败；查看日志和实际 unit 状态，不猜测已切换 |
| `NEEDS_ATTENTION` | 无法安全完成恢复；保留维护/待恢复标记，不强开入口、不自动恢复未知配套的直连服务 |

失败后仅在迁移、插件包/配置/绑定未变且原镜像匹配时自动恢复原应用，不修改或删除插件持久证据。
若曾开放候选公网，回退前重新排空；不能排空则保留维护等待处理。插件临时 `error` 状态不等于包或
配置变更，但恢复后仍必须通过真实健康检查。systemd `ExecStopPost` 处理主任务异常退出；
整机掉电、systemd 自身失效及无法确认的 Docker 操作不保证自动恢复，重启后先核对待恢复标记。

成功发布后需要回退时，在原准备材料仍有效且现场未改变的条件下运行：


## 4. 最小变更切换与验收

1. 持有部署锁，启用维护入口，按已确认范围暂停直连调用方并确认停止，再等待账号/用户并发及实际应用连接排空；不能只看一个计数。
   等待应有明确上限和失败处理，不能为了赶进度强杀在途请求。具体标准见
   [生产可靠性](PRODUCTION_RELIABILITY.md)。
2. 正常停止旧应用，仅更新镜像绑定并重建应用。Compose 场景使用已核对的服务名和
   `up -d --no-deps sub2api`，不执行整套 `down`，尤其不能删除数据卷。
   数据库、Redis、连接池、插件配置及业务规则没有必要变更时保持原状。
   停机结果结合排空证据、容器状态/退出码、是否强杀及正常退出/清理日志判断；
   `context deadline exceeded` 单条日志不足以判定失败，退出码 0 也不足以证明全部清理完成。
   证据不足时先确认结果，不直接继续切换。
3. 检查启动/迁移结果、应用健康、制品身份、关键前端资源、管理员鉴权及相关插件。
   再核对数据库/Redis 容器身份及启动时间、配置差异和历史迁移 checksum；容器 ID 不变不证明未重启。
   区分程序文件摘要和运行进程映像摘要；读取 `/proc/1/exe` 被拒绝时如实标注未验证，不为取证增加容器权限。
4. 本机验收通过后恢复入口，用预先验证的客户端核对公网 HTTPS 健康、关键页面/资源及维护状态已解除；
   临时入口配置恢复原样，并从外部独立核对。公网检查未通过不能记作部署成功。
5. 按原状态恢复临时暂停的服务，核对其实际运行状态、原配置、维护标记及待恢复标记；
   收集独立任务退出日志和验收回执，全部满足后才记录最终成功。

### 失败与重试

- 公网预检出现 `curl: (28) Resolving timed out` 时，先核对失败阶段及旧应用/后台是否实际改变，
  再以相同普通 curl、正常 DNS/TLS 复查入口和资源；不改 hosts、不跳过公网验收来消除报错。
  即使 `PREFLIGHT_FAILED` 尚未进入维护，也保留原尝试，现场复核正常后用新目录重新准备；
  镜像身份和隔离证据不变时可复用制品，不重放旧 `activate`，瞬时复查成功不等于 DNS 根因已查明。
- 公网 403 先按预定检查区分路径、代理/WAF、鉴权与应用错误。本次 `urllib` 与 `curl` 结果不同，
  但具体命中策略未查明，不能直接写成“WAF 误封”；不因验收失败修改 WAF 或关闭 TLS 验证。
  本机证书检查失败时，另从外部以正常 TLS 核对公网。
- 在预定时限内无法确认时，保留证据并按事先确认的兼容回退方案恢复服务，不在维护窗口临时开发
  或连续试切。无法安全回退则保持维护，记录当前宿主、插件和未完成操作，说明阻塞与恢复路径。
- 每次重试前归档上一尝试的脚本、日志、回执和结果，修正问题后重新测试、预检，核对旧任务及锁已结束。
  不直接重放历史启动命令，也不以最后成功覆盖前几次失败。
- 成功的 `systemd` 临时 unit 可能自动卸载；`LoadState=not-found` 既不证明失败，也不证明成功。
  结合 journal、最终验收回执、维护解除及服务恢复状态判断，不能只看 `systemctl show` 的默认退出字段。

**回退应用不会撤销已执行迁移。** 即使失败原因只是验收脚本缺失，新程序也可能已经执行 SQL。
回退后应核对实际数据库状态，不能据“恢复旧镜像”断言数据库未变。默认不恢复旧整库覆盖
上线后的业务数据；若旧程序不兼容新结构，应另行处理，不能盲目切回。

## 5. 收尾与持续复盘

- 更新原有版本记录和部署状态：固定提交、镜像身份、迁移结果、备份/回退路径、验收及未测项。
  当前状态不要残留“尚未部署”，历史记录保留当时事实；文档提交不改变线上程序身份。
- 对用户分别说明准备耗时、维护窗口和返工原因，承认操作遗漏，不把所有耗时都说成必要保护。
  健康检查通过不能代替真实供应商调用、计费、故障切换或压力测试。
- 模型清单变更除核对数量，还应按分组/平台/模型比对保留条目的价格、阶梯及倍率。发现负数或
  波动时保留少量只读样本并在隔离环境复现；单次快照相同不代表计费稳定，参考价异常也不能
  未经核验就断言只影响显示。自动任务 `ACCEPTED` 与后续业务异常分别记录，不能把失败检查写成通过。
- 新返工的预防措施直接写入对应步骤，避免再抄一份经验清单；事故时间线和日志路径放版本记录。
  本文是执行指南，不表示已有自动化检查脚本实现了全部步骤。

## 增量适配与回归保留

- 老板源码和本地包含不同官方移植时，以版本记录中的前次老板完整提交比较真实增量，
  再叠加到本地；直接采用来源整文件会丢失不在该增量内的本地能力。
- 同时比较本地已有测试的删除和预期变化；编译通过或来源测试通过不能证明本地要求仍成立。
  特别核对共享模型缓存、固定清单、首输出包装、WS 智能路由计费、人工暂停及手动终止。
- 调整探针判分时同步核对宿主状态机、插件、健康展示、代理结果归因及持久化回归，
  不能仅修改直接判分测试。按账号类型调整模型缓存时，一并检查 Codex 清单与普通 `/v1/models` 调用方。
- 新增宿主探针许可不能代替已有暂停/终止控制；单账号与批量准入使用相同保护条件。
  新流式结算识别应兼容已有响应体包装，不能因类型断言失败提前取消结算。
- 新版浏览器说明、发布 manifest 与 launcher 必须同步适配 Linux/直连规则；不导入来源项目
  的上线回执或验证结论作为本项目证据。插件版本升级同步两份 GoReleaser 包路径。
