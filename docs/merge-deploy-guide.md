# 合并与部署更新指南

目标：提前准备好新镜像及验收、回退材料，在最短必要维护窗口内完成一次应用切换。
用户要求尽量不动现有环境，但必要的备份、兼容检查和迁移不能省略。
本指南长期维护；每次出现新的返工原因，都把预防措施补到这里，不另建日期版指南。

## 适用范围与记录入口

- 合并范围、个人要求和授权以 [产品规则](upstream-integration-policy.md) 及用户最新答复为准。
  已授权的事项直接执行，不重复询问；新冲突或超出范围的操作先沟通。
- 实现和回归入口见 [当前实现](local-customizations.md)；来源及合并历史写入
  [版本记录](upstream-sync-state.md)，当前线上身份和回退资源写入 [部署状态](deployment-state.md)。
- 本指南用于已有服务更新。不要对现网重新执行初始化安装脚本或覆盖 `.env`、Compose、密钥。
  单服务器更新不等于正式多平台 Release；后者另遵守 [发布要求](../RELEASE-POLICY.md)。

## 1. 固定范围，再合并

1. 记录指定上游完整提交、本项目合并前提交，以及当前生产提交。不能只比较本地最近一个提交：
   上线可能包含此前尚未部署的多轮后端变更。
2. 列出采用、保留、冲突和暂缓项，按已有确认适配，保护个人规则；不整文件覆盖定制。
3. 核对新增迁移、依赖、插件接口、构建输入及前端内嵌资源。按受影响行为完成回归，
   已执行迁移的文件、编号和 checksum 保持不变。
4. 按授权提交、合入目标分支并推送，核对远端完整 SHA；构建固定提交，不使用浮动分支代替。

## 2. 构建前核对线上环境

- 只读核对目标主机、目录、架构、运行镜像 ID、程序提交、数据卷、配置和部署目录 Git 状态。
  目录有历史改动时使用独立检出目录，不能强行拉取、重置或清理服务器文件。
- **先对照 Dockerfile 与线上运行时，再决定构建方式。** 核对浏览器、Node、Python、插件、
  运行用户及沙箱要求；不要构建完才发现 Chromium 降级或插件依赖缺失。
- 普通更新优先保留兼容的运行环境，仅更新应用及配套资源；若依赖确需升级，应明确升级范围。
  沿用旧镜像不是永久冻结依赖，仍须确认新程序兼容和本次安全修复要求。
- 构建与服务切换分开：构建、下载和检查期间旧服务继续运行。提前检查磁盘、内存与构建资源，
  避免挤占生产容量。优先复用已验证制品，不无故反复构建。
- 记录程序提交、镜像 ID/摘要及前端资源身份；候选制品用独立标识，验收后不再覆盖其内容。
  官方版号、项目提交、镜像摘要和 Chromium 版本是不同信息，对用户说明时不要混为一谈。

## 3. 切换前检查：全部准备好才进入维护

- [ ] 新镜像已在目标服务器，架构、提交和资源一致；相关构建/测试及运行时检查已通过。
- [ ] **切换、验收、回退所需脚本全部上传到目标路径**，依赖、权限、语法及引用文件已检查。
      执行可安全进行的只读预检；不得把有写操作的完整脚本当作演练直接跑在生产上。
- [ ] 旧镜像可用，回退步骤明确；提前检查旧程序能否使用迁移后的数据库及新增业务配置。
- [ ] 比较生产已执行迁移与本次制品，列明缺失项、数据清理、锁表和索引影响。
      不重启数据库不等于不迁移；应用启动可能自动执行 SQL，不能承诺“只换镜像就不动数据库”。
- [ ] 完成所需数据库备份、摘要和备份目录可读性检查，保存必要配置快照；
      这些检查不冒充完整恢复演练。备份和凭据只存私有运维目录，不入 Git。
- [ ] 验收项目及失败处理已确定；部署锁可获取，没有另一发布者同时操作。

迁移规则见 [数据库迁移说明](../backend/migrations/README.md)。checksum 必须按当前迁移器
实际算法核对，不能用不一致的原始文件摘要误判。不能通过修改库内 checksum 或跳过必要迁移
掩盖不兼容；新发现的数据删除或不可兼容影响若超出已有授权，先说明并对齐。

## 4. 最小变更切换与验收

1. 持有部署锁，临时停止接收新请求，等待账号/用户并发及实际应用连接排空；不能只看一个计数。
   等待应有明确上限和失败处理，不能为了赶进度强杀在途请求。具体标准见
   [生产可靠性](PRODUCTION_RELIABILITY.md)。
2. 正常停止旧应用，仅更新镜像绑定并重建应用。Compose 场景使用已核对的服务名和
   `up -d --no-deps sub2api`，不执行整套 `down`，尤其不能删除数据卷。
   数据库、Redis、连接池、插件配置及业务规则没有必要变更时保持原状。
3. 检查启动/迁移结果、应用健康、制品身份、关键前端资源、管理员鉴权及相关插件。
   再核对数据库/Redis 容器身份、配置差异和历史迁移 checksum。
4. 通过后恢复入口，核对公网 HTTPS 健康及维护状态已解除；临时入口配置恢复原样。
   失败时保留证据，按事先确认的兼容回退方案恢复服务，不在维护窗口临时调试或连续试切。

**回退应用不会撤销已执行迁移。** 即使失败原因只是验收脚本缺失，新程序也可能已经执行 SQL。
回退后应核对实际数据库状态，不能据“恢复旧镜像”断言数据库未变。默认不恢复旧整库覆盖
上线后的业务数据；若旧程序不兼容新结构，应另行处理，不能盲目切回。

## 5. 收尾与持续复盘

- 更新原有版本记录和部署状态：固定提交、镜像身份、迁移结果、备份/回退路径、验收及未测项。
  当前状态不要残留“尚未部署”，历史记录保留当时事实；文档提交不改变线上程序身份。
- 对用户分别说明准备耗时、维护窗口和返工原因，承认操作遗漏，不把所有耗时都说成必要保护。
  健康检查通过不能代替真实供应商调用、计费、故障切换或压力测试。
- 将新经验写入下表，并同步到对应步骤。只记录可复用结论；事故时间线和日志路径放版本记录。
  本文是执行指南，不表示已有自动化检查脚本实现了全部步骤。

## 已吸取的经验

| 问题 | 下次的预防动作 |
| --- | --- |
| 2026-10-13 构建后才发现默认 Chromium 136 与线上 149 不一致，造成重复构建 | 构建前完成运行时对照并选定方案；仅在新变化或失败需要时重建 |
| 同次部署遗漏上传验收脚本，应用启动后触发回退，补齐后第二次切换 | 维护前检查所有脚本和依赖存在、语法及只读预检；不能切完再准备验收 |
| 服务器检出目录含历史改动，不能直接拉取覆盖 | 先检查目录状态，有改动则固定提交旁路构建，保留运维文件 |
| “只换镜像”“回退成功”容易被误说成数据库没动 | 部署前列出自动迁移；每次启动/回退后核对库内记录，区分应用回退和数据库恢复 |
| 多种版本号及重复构建让进度难以理解 | 面向用户以目标提交和切换结果为主，只有解释依赖问题时才列浏览器等版本 |
| 上游与本地源码没有共同祖先，整树比较会把普通差异误认为冲突 | 仍固定完整上游提交；按行为逐项比较和适配，不做整树覆盖，也不把路径重叠当成行为冲突 |
