## 1. 目标与边界

以当前合并提交 `c832c118ff7dd88a3f0d77f80563f36ba035f389` 为基线，将完整上游 `r17bf` 的救援流程修到可验证、可上线，同时保留我们已有的行为。

本轮的核心不是让几个函数能够被调用，而是让同一个账号走完下面的流程，并在并发编辑、提交失败、进程重启和开关变化时仍能收敛：

```text
判死并符合入区条件
  -> 保存原分组和救援标记，进入救援组
  -> 插件恢复连接，触发资格检测
  -> 检测使用插件传输，得到真实结果
  -> 成功提交检测结果
  -> 恢复原分组，清救援标记，记录恢复结果
  -> 中途失败时由清扫重试完成
```

必须保持的行为：

- 无代理 OpenAI OAuth 可以授权、导入、调用、检测和重新授权。
- 配置了代理时继续校验代理；无效的代理配置不能自动改为直连。
- 普通新账号导入后立即启用；救援账号仍按救援资格检测规则恢复调度，两者分别验收。
- 我们已有的手动暂停、影子账号代理继承和其他定制行为继续成立。
- 保留上游新插件、签名发布、升级错误保留和部署版本隔离机制。
- 继续使用 rescue lane；已替换的 harvest/ticket 流程不恢复。

修复优先复用现有临时执行器、原子提交、行锁、专用 Extra 更新和清扫机制。当前问题预计不需要新增表或依赖。

## 2. 已确认问题及共同原因

| 问题 | 已有证据 | 本轮处理 |
| --- | --- | --- |
| 资格检测绕过 Cookie 钉扎插件 | 临时执行器遗漏 `pluginRoundTrip`，回归已复现 | 传递传输能力，并验证实际检测路径 |
| 检测通过后没有立即恢复原分组 | 临时执行器没有 `rescueLane`，提交后也没有转正调用，回归已复现 | 将转正放到成功提交后的正式执行器上 |
| 旧账户表单覆盖救援状态 | 服务层整体替换 Extra，数据库保护未覆盖救援字段，删除和复活标记均已复现 | 在数据库行锁下保留当前救援字段，并保护管理端各写入口 |
| 关闭救援后无法补偿转正失败 | 清扫在开关关闭时整体返回 | 允许已合格账号继续完成退出，其他救援动作仍受开关控制 |
| 部分导入测试沿用上游代理限制 | 前端重新授权和后端重新授权仓库测试失败 | 按已确认的直连规则修改测试，并保留有代理覆盖 |

前三项在上游代码中也存在。本轮修复应覆盖整个调用链，而不能仅以“与上游一致”作为正确性依据。

## 3. 实施顺序

### 阶段一：固定行为和失败基线

将复核时的临时回归转为长期测试，先确认它们能复现原问题。记录当前相关测试在我们原版本、上游版本和合并版本中的结果。

明确两个实现约束：传输能力可以进入临时执行器；修改正式账号分组和救援状态的动作必须在检测提交成功后执行。

产出：可复现的回归测试、定制行为清单、已有测试失败清单。后续每个修改都能说明修复了哪个失败，并证明没有改变直连规则。

### 阶段二：保护救援数据的所有管理端写入口

主要涉及 `backend/internal/service/admin_account.go`、`backend/internal/repository/account_repo.go`，并对照已有的 `oauth_reauthorization_repo.go` 保护规则。

- 普通整行更新在已有行锁下读取数据库当前 `openai_rescue_*` 字段；移除请求快照中的同名前缀字段，再合入数据库现值。
- 数据库当前没有的字段不能由旧表单恢复；当前存在的字段不能因表单缺失而删除。保持现有 JSON 空值语义。
- 服务层同步保护当前救援字段；并发正确性的最终保证放在数据库更新层。
- 管理端单独 Extra 更新、批量编辑和重新授权使用一致的受管字段规则。
- 救援服务自己的专用写入仍可以创建、更新和清除这些字段。不要在共享 `AccountRepository.UpdateExtra` 中无差别禁止救援字段，否则会阻断救援服务本身。
- 检查旧表单中的分组载荷与救援自动改绑的交互；如发现能覆盖当前救援绑定，补充复现，并在实施中先明确冲突处理规则。

验收：旧表单保存、显式空 Extra、批量编辑和并发救援状态更新都不能删除当前标记或复活旧标记；普通用户设置仍能正常修改，救援专用写入仍然有效。

### 阶段三：接通检测与提交后的转正

主要涉及 `backend/internal/service/openai_downgrade_commit.go`、`backend/internal/service/openai_downgrade_probe.go`。

- 在 `stagedRunner` 中传递 `pluginRoundTrip`，保留临时存储和正式写入隔离。
- 验证“救援账号且插件处理请求”实际使用插件；插件没有处理时按原规则使用一次性传输；插件已经处理但返回错误时保留错误。
- 将资格检测通过的转正动作放到 `processStateAtomic` 成功提交分支，通过正式执行器调用现有 `GraduateRescue`。
- 用本轮资格通过的状态转换或最小暂存标记识别需要转正的账号，避免每次普通检测都触发转正。
- 提交失败或陈旧结果被拒绝时，不改变原分组、救援标记或恢复次数。
- 数据库提交成功但缓存刷新失败时，仍执行提交后的转正，并保留原缓存错误；不能把已提交结果当作回滚。
- 转正执行使用有时限的上下文；转正失败记录账号和失败阶段，保持检测结果有效，交由清扫补偿。
- 即时转正和清扫重复执行时，复用当前标记检查；验证不会错误恢复新一轮救援的旧分组，也不会重复累计同一轮恢复次数。出现竞争漏洞时在现有提交边界增加最小保护。

验收：真实原子执行路径中的资格检测命中插件；通过且提交成功后立即恢复原组；未提交不转正；转正失败不撤销已通过的检测结果；无代理、有代理、非救援账号的连接规则保持正确。

### 阶段四：补齐清扫和开关变化后的收尾

主要涉及 `backend/internal/service/openai_rescue_lane.go`。

采用与现有 `GraduateRescue` 注释一致的语义：关闭救援停止新的救援动作，已通过资格检测的账号仍能完成退出。

- 将“已有救援标记且状态为 `on_duty + normal`”的转正补偿放到新入区、补种子等动作的开关判断之前。
- 当 `Enabled=false` 或救援组配置被清除时，仍可从原分组记录完成已合格账号的转正；不依赖当前救援组配置。
- 开关关闭时不补进新账号、不补种子、不触发新的自动资格检测、不重新绑回救援组、不自动开启调度。
- 资格检测在途或仍未通过的账号不能被当作已恢复账号转正。
- 覆盖“恢复原组成功、清标记失败”和“成功提交后进程退出”的中断点；下轮能继续完成，账号不会被反复送回救援组。
- 对手动暂停和并发状态改变做回归，确保补偿不会绕过用户的暂停选择或使用过期恢复证据。

验收：即时转正失败后，无论救援开关是否关闭，已合格账号都能被清扫收尾；关闭状态下不会额外产生救援上游请求。

### 阶段五：测试适配与整体验收

先修正与既定规则冲突的测试，再扩大验证范围。测试应验证行为，不能仅修改预期值来消除报错。

| 验证面 | 必须覆盖的情形 |
| --- | --- |
| 连接路径 | 救援插件处理、插件未处理、插件处理失败、普通账号、有代理、无代理 |
| 检测与提交 | 通过、失败、提交失败、陈旧结果、重提交成功、提交成功但缓存失败 |
| 转正与清扫 | 即时成功、恢复分组失败、清标记失败、重复执行、进程重启、开关关闭、配置清除 |
| 状态保护 | 旧表单、空 Extra、单独 Extra 更新、批量更新、重新授权、并发写入、系统专用写入 |
| 手动终止 | 原组恢复、停调、暂停资格检测、不计恢复、自动入区抑制、终止后编辑和手动重入、并发毕业、事务失败回滚 |
| 插件停止 | 在途取消、迟到回包、暂停期间请求跨越重启、启动/多实例同步、普通配置保存/回滚不能解除暂停、旧插件拒绝配置 |
| 我们的定制 | 直连授权和调用、导入立即启用、清除代理、无效代理拒绝、手动暂停、影子代理继承 |
| 上游新功能 | 插件完整测试、发布替换测试、签名校验、升级失败记录和部署版本隔离 |

修正两套重新授权弹窗测试：有代理时显示代理浏览器入口，无代理时保持普通授权流程。更新重新授权仓库测试的代理查询和校验预期，继续覆盖有效代理、无效代理和陈旧凭据更新保护。

修正本次涉及的旧资格检测和导入测试，使其观察正式原子提交结果，并区分普通导入立即启用与救援资格通过后启用。

执行后端编译、相关服务/仓库/管理接口测试、插件完整测试、发布替换测试、前端相关测试、类型检查和生产构建。随后在独立 PostgreSQL 环境验证迁移、行锁并发、原子提交和调度快照；SQL 模拟测试不能替代这一步。

较大范围测试中的其他失败逐项对照父版本，记录为本轮回归、已有测试问题或已有功能问题。与本轮连接、凭据、救援和状态保护相关的失败必须解决；其他问题单独列明影响，不能隐去失败后宣称全部通过。

手动终止必须同时覆盖宿主和插件的独立探测循环。终止名单以数据库为准，插件启动和每秒对账时同步，本实例终止/重启时立即尝试同步；普通插件配置不拥有终止名单。同步失败停止本实例该插件进程，并由后续对账重试。手动重入先解除插件暂停，再发送新种子，不能继承旧探测证据。本地插件修复版为 `0.3.8`，与宿主共同验收和发布；实际发布签名与信任配置仍需单独验证。

## 4. 现有数据与发布准备

代码修好只阻止继续出错，还需要确认运行环境里是否已有受影响账号。

先做只读检查并生成账号清单：有救援标记且已经合格但仍在救援组、恢复原组后标记残留、处于救援组却缺少有效标记或原分组记录。

- 原分组记录完整且符合转正条件的账号，优先由修复后的清扫完成恢复。
- 缺少标记或原分组记录时，只从可靠备份或事件记录恢复；无法确定时列为待人工确认，不猜测分组。
- 发布前记录数据库备份、插件版本、救援开关、救援组和部署版本，核对恢复所需的原分组仍然存在。
- 在隔离环境用少量专用账号验证完整流程，包括直连账号和代理账号；真实上游请求及生产部署属于后续执行步骤，按当时授权进行。
- 回滚方案采用与现有 rescue 数据兼容的程序和插件版本。旧 ticket 表已删除，不能仅靠退回旧程序恢复 harvest 流程；涉及旧流程恢复时必须单独处理数据库备份。

## 5. 完成标准与交付

- 已复现的三项功能问题均有长期回归测试，并在修复后通过。
- 救援流程能完成进入、插件检测、提交、即时转正和失败补偿；关闭救援不阻断已合格账号退出。
- 普通管理操作无法覆盖救援服务拥有的状态，数据库并发验证通过。
- 我们的直连、立即导入和既有定制行为有明确验证结果。
- 后端、前端、插件和发布相关检查结果逐项列出，剩余失败及限制可追溯。
- 历史异常账号有处理结果或明确的人工待办。

建议按“回归基线、受管数据保护、检测与转正、关闭状态补偿、测试适配”拆分可审阅提交；部署时将通过整体验收的修复作为一个版本发布。

最终交付包括代码提交、测试结果、剩余问题清单、异常账号清单以及发布和回滚说明。
